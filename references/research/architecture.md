# 配单 / BOM 采购能力 —— 架构草案（Lead，迭代中）

> 状态：草案 v0.1，2026-11-04。带 `【待验证】` 的条目等队友报告回填。
> 目标：让 agent 在真实中文元器件电商上完成「检索 → 指标对比 → 选型 → 渠道推荐 → 报价单」闭环。

## 1. 能力边界（要解决什么）

| 场景 | 输入 | 期望输出 |
|---|---|---|
| 单料选型 | 型号 / 关键词（如 "STM32F103C8T6"、"10k 0603 1%"） | 候选表（价格阶梯、库存、销量、品牌、封装、参数）+ 推荐理由 |
| 无思路选型 | 品类需求（如 "3.3V LDO 500mA SOT-23-5"） | 按销量/性价比排序的常用料，附风险提示 |
| BOM 配单 | BOM 文件（xlsx/csv/立创EDA 导出）或粘贴清单 | 逐行匹配立创料号 + 价格/库存 + 替代料 + 总价 + 缺料项 |
| 跨渠道比价 | 已选料 + 数量 | 立创 / 淘宝 / 1688 的价格与可得性对比 + 渠道建议 |
| 指标对比 | 2~N 个候选 | 对齐后的参数表 + 差异高亮 + 是否可直接替换的判定 |

## 3. 交付物形态

一个 skill：`skills/bom-sourcing/`

```
bom-sourcing/
  SKILL.md                # 触发条件、工作流、决策规则、坑
  scripts/
    lcsc.py               # 立创检索/详情/价格阶梯/BOM 批量匹配
    taobao.py             # 淘宝检索（浏览器驱动，输出结构化 JSON）
    bom.py                # BOM 解析 → 匹配 → 汇总 → 渠道建议
    report.py             # 生成 Markdown/CSV 报价单
  data/
    spec_rules.yaml       # 指标对比与替代规则（spec-rules 产出）
    channel_rules.yaml    # 数量→渠道 推荐规则
    parts_default.yaml    # 常用料默认选型（阻容、LDO、MCU 等）
  references/
    lcsc-api.md           # 可复放 API 清单
    channels.md           # 渠道特性与坑
```

设计原则：
1. **结构化优先**：能拿 JSON 就不解析 HTML；立创是首选数据源（价格阶梯/库存/销量齐全）。
2. **指标先于价格**：先按 spec_rules 判定"同规格"，再在合格集合里比价；不允许"便宜但降规"。
3. **数量分档**：同一料号按 qty 取不同阶梯价 + 不同渠道，输出"少量方案 / 批量方案"两列。
4. **可复放**：每次查询落 `probe/` 或缓存 JSON，便于复盘价格。
5. **不造轮子**：优先用现成库/CLI（待 gh-research 结论决定）。

## 4. 核心算法

### 4.1 数量分档（渠道推荐）
```
qty <= 10        → 淘宝优先（散卖、包邮、开发板），立创兜底
10 < qty <= 100  → 立创（正品、有票、可贴片）+ 淘宝比价
qty > 100        → 立创批量阶梯 / 1688，淘宝仅作替代料来源
```
【待验证】各渠道实际起订量、邮费、含税差异。

### 4.2 指标合格判定
- 由 `spec_rules.yaml` 描述每类器件的关键指标与容差（如 LDO：输入范围、输出、压差、电流、封装；MCU：内核/主频/Flash/RAM/封装/温度等级）。
- 候选必须满足全部硬指标；软指标（品牌、交期、封装偏好）参与打分。
- 输出时必须显示"哪几项指标不一致"，不能只说"可替代"。

### 4.3 无思路选型（销量启发）
- 立创：`sortNumber=6`（销量降序）+ 关键词；
- 淘宝：搜索页按销量排序（待确认参数/交互）；
- 交叉验证：销量高 + 指标满足 + 单价处于同规格中位数附近 → 推荐。
